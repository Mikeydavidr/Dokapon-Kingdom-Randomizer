# Board data notes (PC version)

Decoded by matching the overworld continent screenshot against board 0. All 68 spaces on that continent
matched the legend colours one for one, and the 10 town spaces matched their town signs.

## Files
| File | Holds |
|---|---|
| `Data_eng/dataSeq_EN/stgNNN_EN.DAT` | one 16-byte record per space: `33 00 00 00`, index u32, type (2 bytes), group (1), 00, param (4 bytes) |
| `CommonData/fieldChain/CHAIN_NNN.DAT` | u16 count, then per space: id + 4 neighbour slots (u16, `FFFF` = none). Links are always two-way. The slot is the DIRECTION: 0 = +z, 1 = +x, 2 = -z, 3 = -x (true of all 754 links on board 0), and the reverse link uses slot (i+2)%4. So every road is axis-aligned. A link in the wrong slot or between spaces that are not on one axis lands fine but crashes the game when auto-path routes through it. Roads are drawn by the map model, not from this file: cutting a link leaves the road on screen. |
| `CommonData/fieldPosition/MASUNN.position` | node names (`Z0000`...), then x/y/z float32 per node |
| `Data_eng/dataSeq_EN/stageBase_EN.DAT` | space-kind names (marker `87`, from 0x5B0), town/castle table (marker `6D`, from 0xF34) |
| `CommonData/map/NamePlate_EN.texpack` | the board's name signs: 82 PNGs, 256x64 |

Board 0 is the overworld (337 spaces). Its screenshot is rotated 180 degrees from the board's x/z axes
(screen x = -1.17 * x + 136, screen y = -1.17 * z + 459 for the first continent).

## Space type, first byte = kind (names come from stageBase_EN.DAT)
`01` Item, `02` Magic, `03` Red Loot, `04` White Loot, `05` Locked Box, `06` Money, `07` Weapon, `08` Shield,
`09` Battle Magic, `0A` Bank, `0B` Collection, `0C` Poison Swamp, `0D` Snowfield, `0F` Warp, `11` Dark, `12` Trap,
`13` Doom, `14` **Town**, `15` **Castle**, `16` Weapon Store, `17` Item Store, `18` Magic Store, `1B` Casino,
`1C` Coliseum, `1D` Dokapon Castle, `1E` Plain, `1F` Forest, `20` Mountain, `21` Desert, `22` Ocean, `23` Swamp,
`24` Cave, `25` Lava, `26`-`5D` dungeon names and entrances/exits (`2D` Spring Cave Entrance, etc.).
Run `decode_tables.py` for the full list.

Second byte of the type: `FF`, or a skin value (it repeats in `param` for towns).
The overlay legend "Empty Space" is any of `1E`-`25` (terrain) plus `0D`/`0C` when the area has that effect.

## Monster encounters
Tested in game (`void_enc`, starting area pointed at a Skeleton-only first table and a Bat-only second table): only Bats in a Normal Mode game and only Skeletons in Story Mode, on land and sea alike. So the space's tables choose the monsters regardless of terrain, and **the first table is Story Mode's, the second Normal Mode's** (Normal Mode's lists have more copies and a rare Rico Jr.).
Each empty space picks its own encounter tables: for the terrain kinds `1E`-`25` and `0C`/`0D`, `param` = `[table u16][second table u16]`. The second table is the first + 29 (`0x1b`/`0x38` = Plain on continent 1); in the starting area (group 0, which has plains, forest, mountain, desert, snow and sea) both are mostly the same (two spaces differ). The first table holds a few monsters, 1-5 copies each (the copies are the odds). The second has the same monsters, sometimes some others, mostly 5-15 copies each, and usually one copy of Rico Jr. (118). When the game uses the second table is not known. The group byte is the area (0 = start, 1-6 = continents) but does not choose the monsters: a space with an ocean table gets sea monsters wherever it is. Item, magic and red loot spaces use `param` the same way for their loot table (the `0x7f` index at 0x3928).
Tables: `stageBase_EN.DAT` 0x25060 holds 160 u32 pointers; list i starts at pointer + 0x8350 and is monster ids (u8, as in the `0x50` monster records) ending in `FF`. Board 0 uses tables `0x15`-`0x4e` and `0x6d`-`0x6f`; boards 1-9, 15 and 22 use `0x00`-`0x09`, `0x0f` and `0x4f`-`0x5d`. Not used by any space: `0x61`-`0x69` (dungeon monsters mixed with the scaled copies 131-135), `0x6a`-`0x6c` (only Wabbit, Chimpy, Robo-Sassin: event battles?), `0x82`-`0x8f` (short lists of mixed monsters), and the placeholders `0x70`-`0x81` (Rogue x10, one shared list) and `0x90`-`0x9f` (Rogue x5). An earlier pointer table (0x24f??-0x24fb8, lists of 2-3 ids from 0x24fbc) is not decoded; a guess is the monsters that can take over each town.
The lists fill 0x252E4-0x259CC with one spare byte; the next record follows (11 more bytes come free by storing identical lists once). stageBase is chunks (`@BAS` 0x8348 bytes, then `@CHR` at 0x8350: magic, u32 size including the header, 0x30), and `@CHR` is a script of tagged records run at load; pointers count from the start of `@CHR`. Data blocks are skipped with a jump record `03 00 00 00 | target - 0x8350` (the one at 0x24ECC jumps over both pointer tables and the lists to 0x259CC). The chunk ends at 0xB1258 with records `79` and `63 0F` (a record at 0xB1220 points at the `79`), then 8 bytes of padding. `encounters.py` puts lists that no longer fit after the last record and grows the chunk size (`void_grow`, tested in game: the starting area's Bat table and a 200-entry Zombie-then-Gremlin table for the 6 empty spaces within 3 steps of Dokapon Castle all live there, and both Zombies and Gremlins turned up near the castle with Bats elsewhere and no crash, so the game loads the grown chunk and reads whole lists of any length placed there). A pointer table record `4F 00 00 00 | 0x1CD10` sits at 0x24D3C. Monsters whose stats have bit 0x8000 set scale with the player (Demon's Guard 104, Rico Jr. 118/136, the Overlords, Clonus, Wabbit, Chimpy, Robo-Sassin, the copies 131-135): keep them out of ordinary tables.
`encounters.py` reads all this out to a JSON file (tables as monster -> copies, every empty space with its two tables, which spaces use each table) and builds it back in (unchanged files come back byte-identical); `--map` draws board 0 with each empty space labelled by its first table. `tools/testpatch/make_encounter_test.py` is the in-game test: one area's empty spaces all point at two one-monster tables (default Skeleton first, Bat second).

## Town and castle spaces
`param` = `[town id u16][skin u16]`. Town id 8 = Ural. Castle ids (`15`) start at 0x32 (Khan's Castle).
Stores and the Coliseum have no id in `param`.

## Town table (stageBase_EN.DAT, marker `6D`, 55 records)
`6D 00 00 00 | id | continent | byte | 00 | name (null-terminated, padded to 4) | u32 | price u32 | u32`.
Name field capacity is the padded length (Ural: 8 bytes, 7 characters usable).

## Signs
`NamePlate_EN.texpack`: u32 count (82), 12 zero bytes, count x `[4 byte tag][u32 PNG size]`, then count x
`[16 byte name "NN.png"][PNG][pad to 16]`. Sign number = position in the town table + 3
(0-2 are the stores; castles follow the towns; temples, casino, caves etc. follow).
Not yet checked: whether the game ever builds a sign from text.

## What was tested in game (board 0)
- Swapping type + group + param between two space records: stores, towns and plain spaces all work (rules, shop stock and the sign follow the record). The building art does not follow.
- Building art: `dataField/F00/F00_{N,M,A}.model`; see `tools/igb/igbmodel.py`. Store, town-disc and castle buildings are placed by a 4x4 matrix in the file's MTRX chunk (translation in the last row), usually about 25 units from their space. Changing a matrix's translation moves the building (a game restart is enough, the installer repacks the model). Building to matrix: F00_M 24 castle 170, 43 magic 87, 5 magic 152, 44 magic 268, 20 item 122, 2 item 218, 45 item 237; F00_N 1 castle 76, 37 castle 311, 46 item 18, 14 item 59, 32 magic 287, 33 item 314. Weapon store 105 is baked into the geometry (not matrix placed). The Magic Store building is the purple potion with a star book and a wand; the Item Store is the blue building with a heart or window.
- Keep each building's own offset from its space when moving it, or it floats or sinks (ground height differs per area).

## Space kinds at run time (live tests, `tools/live/space_kinds.py`)
- The running game keeps one 192-byte record per space (board 0: 337 in a row, ordinary heap memory). Around the kind byte K: x, y, z floats at K-24, a flags u16 and the space index u16 at K-8, the param (4 bytes) at K-4, the kind at K, the skin (second type byte) at K+2, then per-space data that changes as players move (pointers, a packed block of 2-bit values). The board file is also loaded raw (16-byte records) into a buffer that is reused.
- Changing the kind in the record changes the info panel's text at once, and it lasts through turn changes. The disc art does not change.
- After a battle, the game reads the board file into the same buffer again and rebuilds every record in place, which undoes the change. A mod that changes spaces during play has to apply its changes again after every rebuild, for example with an exe patch in the routine that builds the records.
- A loot kind needs a loot table in the param: setting Plain -> Red Loot and keeping the encounter param 0x72 crashed the game on landing. Red Loot on board 0 uses tables 0x0D-0x13 (one per area). White Loot appears only in dungeons (boards 5-21, tables 0x19-0x1E). Landing on a changed space with a valid table has not been tested yet.
- Landing works once the param is right: space 40 set live to White Loot with table 0x19 gave a Squid Ring.
- Not every battle rebuilds the board: one battle reset the records, a later one did not.
- The second type byte is not the disc look (plains 1E, ocean 2B, forest 2A, Dark space 49 also 1E).
- Disc art:
  - The disc textures are the 19 PVRs in `CommonData/map/Masu_Texture.texpack`, named by kind: wa, n, kt, i, shu, as, s, m, a, k, dk, go, buki, tate, btlmg, mgfo, devi, kinshi, in (`*_masu.pvr`). The exe loads them at file 0x21EAE0.
  - Each disc is a square 18 units wide at the space, using the whole texture (UV 0-1). It is drawn as a triangle strip of 6 vertices of 24 bytes (xyz float, colour u32 = ffffffff, uv float x2), so 144 bytes per disc, the extra 2 vertices being duplicates that join one disc to the next.
  - The game groups discs into one batch per texture (Item, Magic, Red Loot, Bank, towns/stores, dungeon entrances, empty terrain...) and puts them in two write-combined (GPU upload, Protect 0x404) buffers that it builds once and then draws from. Editing those buffers changes the board at once: swapping the xyz of space 36's disc (plain batch) and space 39's (Item batch) in both buffers made 36 show the Item disc and 39 the plain one, tested.
  - The ordinary-memory copies of the same quads (per area) are not what is drawn: editing them did nothing.
  - So a disc's look can be changed by moving quads between batches (a swap needs no new space). Giving a space a texture that has no spare quad needs a spare disc in that batch, or code that rebuilds the batches.

- A battle reads its space's kind as the terrain (exe RVA 0x16CEB1: kinds 0x1E-0x47 index a table of 56-byte entries at RVA 0xABE440, anything else gives a null pointer). Changing a space's kind to a non-terrain kind during a battle on it crashed the game (dynspaces v1), so a space must not change while it is the current space.
- After loading a save, the calendar block read week 1, day 0 until a battle started, then the real week (2).

## Calendar (found with `tools/live/memscan.py`, snapshots on Mon wk 1, Sat wk 1 and Sun wk 2)
- The exe global at RVA 0x8A8408 (in .data) points at the game state block + 0x20. Week = u16 at pointer + 0x1C (1 in the first week). Weekday = u16 at pointer + 0x1E (Sun 0, Mon 1 ... Sat 6). A new week starts on Sunday, and the first game day is Monday of week 1. The u32 at pointer + 0x04 went from 1 to 0 at the week change (meaning not known).
- The state block is a 1.7 MB heap allocation, near the space records.
- The global at RVA 0x8A81C0 points into one space's record (24 bytes before the kind, at the x position), apparently the current space.

## Signs, shadows and the live tools (board 0, all tested in game)
- Nameplates (the wooden store/castle signs and the purple town pennants) are placed by a list at the end of `stg000_EN.DAT`: 92 entries of `u32 0x92, u16 space, u16 plate` starting at the entry for Item Store 18. Plate 1 = item store, 2 = weapon store, 3 = magic store, 4.. = individual towns, castles and so on (castles 52..58). Editing the space moves the plaque; swapping two spaces' records without swapping their plaques leaves the signs on the old spaces. `make_board_test.py` does both.
- Right after it, 52 entries of `u32 0x91, u32 space, u16, u16` place the signs of stores, castles, temples and the like: item stores 30/22, magic stores 32/12, weapon stores 30/17 or 30/12, castles 35/10, 32/20 or 35/20. The second number is how far back the sign stands: a castle moved to an item store's space without its entry got the store's 22 and its sign ended up behind the castle's tower (seen in game). `stage.py` moves these entries with the record. The plate artwork is `NamePlate_EN.texpack`; an earlier test's shuffled copy stays patched in the CPK unless the vanilla one is shipped in the mod.
- Shadows are not tied to the building matrix. The ones tested are small flat clusters of vertices inside shared batch meshes (`F00_A` meshes 29 and 30 hold translucent patches of many kinds: building shadows, tree shadows and green water pools). A shadow can be moved by shifting only its cluster's vertices. Found so far: Magic Store 152 -> a 4-vertex square at about (317, -53) in `F00_A` mesh 30 (the building matrix sits 28 units from the space, so look near the building, not the space); the fan at (343, -102) is a tree. Item Store 218 -> `F00_A` mesh 18 (10 vertices, world positioned). The shadow of Item Store 59 is not in `F00_A` and not under an `F00_N` matrix.
- Everything is testable without reinstalling while the game runs on the board: `tools/live/matrix_poke.py` (one matrix), `matrix_live.py` (step through all matrices with pad or keyboard), `hide_near.py` (hide all matrices near a space), `mesh_poke.py` (collapse or show a mesh piece), `shadow_move.py` (shift one vertex cluster of a mesh). The game keeps both the matrices and the vertex data in ordinary writable memory, two copies each, and redraws from them.
- Stores and castles are listed as units in `board0_buildings.json` (building + shadow + decor), moved together by `units.py`; `tools/testpatch/make_unit_swap.py` swaps records, signs and units. Weapon stores and castle 14 are not movable yet (only their shadows are mapped).

## Model files: what each piece is (from the files, not yet all tested in game)
- The chunks follow one another after the textures (`TEXT VERT INDX DECL GEOM UNIF MATR MTRX CHLD NOD2 TERM`), each size counting its 8-byte header; offsets are relative (GEOM into VERT/INDX), so a mesh piece can grow: `igbmodel.rebuild` repacks VERT and INDX (INDX padded with 0xFF) and fixes GEOM and the piece's bounding box in NOD2. With no edits it reproduces all six F00 files byte for byte. The installer stores a larger file whole in the CPK (checked by searching the CPK for the file's bytes).
- `NOD2` is the scene tree, 13 words per node: `[MTRX offset or -1, child count, bbox (own coordinates), CHLD byte offset of the children, MATR, GEOM, 1 for a mesh, name]`; `CHLD` lists the children as u16 node indices. A piece reaches the board through the product of the matrices on its path to the root (`Model.placement`): many terrain and road pieces are stored scaled down by 1.5 or shifted far off the board (the whole south-centre continent, the roads around 68-78), and in `F00_Anim1` a group shifts by +564 while its children shift back by -564. Without this the south-centre continent is missing and several roads sit off their spaces. It names every piece (a layer name such as `road_01`, `road_side`, `road_shadow`, `town_01`, `green_01`, `jimem_01` = ground, `sea_01`) and gives its material; `MATR` names the material's texture. `tools/igb/render_top.py` draws the whole board from above, buildings included, through these matrices.
- Terrain kinds share textures (`green_01`/`test.tga` is grass and sand; the desert floor is `town_01`/`objes.tga`), so `roads.ground_kind` tells grass, sand, snow and water apart by the texture colour under a point. The render tints some grass blue where the game does not (the `_Water` shaders ignore the vertex colour).
- Vertex layout: position 3 floats, normal 3 floats, colour 4 bytes at 0x18, uv 2 floats at 0x1c, and in the 44-byte layout 8 more bytes at 0x24 (copied, not interpolated).

## Roads (board 0)
- Roads are flat triangles in the `road_01` layer textured from the road part of the `fieldC.tga` atlas: a ragged dirt strip about 22 units wide with a white-and-orange line down the middle (u 0.5..0.75, v 0..0.29 per 49 units), the line alone (the row at v 0.48), the rounded cap (v 0.625..0.748, no line), the T tile (u 0.75..1, v 0.25..0.5) and the line turning blue towards water (u 0.86..0.9, v 0.5..0.63). The same pieces also hold bridges (planks at u 0.375..0.5), ice patches, pools and flowers, so `road_uv` lists the road regions exactly.
- What the game draws (seen in game): every road has the orange line with its white outline; it has the dirt strip under it only between two grass spaces, on sand, swamp, ice and snow just the line. Over water the line turns blue/purple, and links between two water spaces are animated water paths, not road strips.
- Every space where roads meet has a junction tile, a square 11 units either side of its road centre (which sits 1 unit -x of the space position), and the strips run from tile edge to tile edge (some straight runs pass several spaces in one strip). Tiles: dead end = the cap from 1 unit behind the centre to 11.6 past it, plus the strip from the edge; two roads in line = a straight square; a corner = a strip square folded on its diagonal (inner corner u 0.502, the side corners u 0.748, the far corner 0.17 further in v); three or four roads = the T tile, its branch towards u 0.752; line-only roads = the line from the centre to each edge. The space disc covers about 9 units around the centre, hiding the tile's middle.
- `roads.py`: `cut(a, b)` clips the strip between the two tiles and draws both tiles again for the roads they keep (a T that loses its branch becomes straight, a corner end becomes a cap); `add(a, b, style)` draws the strip between the tiles, following the ground, and redraws both tiles; `style_for` picks dirt for two grass spaces, else the line. `check_new_link` refuses diagonal links, taken direction slots, links through a space, links that cross a road or water; `check_cut` refuses sea routes and bridges (they are not road strips). `tools/testpatch/make_board_seed.py` builds a board from explicit or random swaps, cuts and adds. A moved shadow that would lie on a road or space, on other ground than its building, or over another decal of the road_shadow layer (dune glows, pools, other shadows) is shrunk to 90% at most or else dropped (`units.Art.fit_shadows`): seen in game, a shrunk shadow loses its front under the building and a misfit one looks worse than none (castle 123 at 122 over the beach, castle 260 at 268 over the space behind, the grass and a dune's glow). Shadows float 2-5 units above the ground, so the tilted camera shows them further back than they are.
- The links form three groups of spaces that are not joined by links (234, 51 and 52 spaces); a cut must not split one.

## Laying out a board freely (void board probe)
- Tested in game (`void_wide`, spaces spread x1.15): the flat grass world, the moved spaces, the town models (TW_LOC) and the moved buildings all showed up right. The camera stopped short of the outer spaces on every side but north: `stg000` record `13 00 00 00` holds the camera limits as s16 x max, z max, x min, z min (vanilla 600, 400, -650, -800; the spread board reached 637, 378, -729, -867, so only z max still fit). `make_void_board.py` now moves the limits with the board, keeping the game's margins (tested: the camera reaches every space).
- Structures the size rule missed (seen missing in game): Yukon (123) and Cusco (199) castles, magic store 2 and the Coliseum (3) are clusters inside big `town_01` pieces (M5, M2, N59), now cut out by area; the Lava Cave is the two clusters near (413, 66) of the `mountain_01` piece A25 (the rest of A25 is the mesas by spaces 124-128; keeping the whole piece brought them along, seen in game) with smoke `Anim2` 9; the Sunken Shrine (180) is the whirlpool `uzu_01` (`Anim2` 0/1, at sea level, so it has to rise onto the grass). The Lost Forest entrances (164, 187) have no art of their own (the forest is the art).
- Falling snow around Sermitsiaq (177) and Strom Castle (170) still shows on the void board, so it is not model art (the flake is `SNOW.png` in `Data_eng/pil2D_EN/GAMEEFF_EN.PIL`). It does not follow the Snowfield (`0D`) spaces (tested with `void_snow`, `tools/testpatch/make_kind_test.py`: island Snowfield spaces made Plain, three plains by the starting castles made Snowfield; the snow stayed on the island only). It is particles over that island, drawn whenever the island is in view (`SNOW.png` is image 4 of the effects file's 10). Found with `tools/live/scan_snow.py` (reads the flakes out of the running game): one emitter `[centre x, y, z, 0][flags][half-width][top y][bottom y][1.5]...`, flakes over centre +- 125 in x and z, falling from y 175 to 0. Its set-up function (exe file 0x213CB0) writes the board 0 centre as immediates (`mov dword [rdi], 120.0` at 0x213D2A, y 10, z 250 at 0x213D37) and loads the half-width (0x213D1E) and top (0x213D14) from shared .rdata constants (125.0 at 0x4BBE00, 175.0 at 0x4BBEB4). It is hard-coded to the vanilla island: it did not follow the spread-out void board. Tested in game: moved onto Dokapon Castle (void board, centre -484, -87) with half-width 60, the snow fell there, smaller, and the island had none; nothing else changed. `tools/testpatch/make_snow_patch.py` writes a `.hex` for the installer: any centre, a half-width/top by pointing the load at another constant with that value, or `--off` (centre far away). The function's other branch (argument 0x24 or 0x28, probably other boards) has its own settings, untouched.
- `MASU00.position` W points look like path waypoints (from the data, not tested): `stg000` record `34 00 00 00`, then entries `space, W index..., space, FFFF` (31 entries using W0-W31), probably the bends a piece walks through between two linked spaces (bridges, sea routes).
- Animated pieces turn about their own origin: Daunting Mountain and its cloud rings (`Anim1` 3-8, one parent matrix at 564, -615) and the whirlpool must be moved by their matrix. Moving their vertices made the clouds circle the old spot (seen in game).
- Towns have no building in the F00 models: the game draws them at the points of `CommonData/fieldPosition/TW_LOC.position` (48 points `TZ<c>V<nn>`, one per town space, about 25 units from it; probably the continent and the town's index). Moving a town means moving its point. `MASU00.position` also holds 32 `W` points after the spaces, each 10-40 units from a space (use not known).
- `tools/testpatch/make_void_board.py` strips board 0 to a flat floor of tiled grass (`test.tga` repeats every 60 units) with every road drawn again from the links, keeps the sky and the buildings (town_01/block_01 pieces under 70 units across), sets every space to one height and, with `--scale`, spreads the spaces out (link directions unchanged). Buildings, TW_LOC and W points move with their nearest space. A piece is hidden by replacing its geometry with one degenerate triangle.
